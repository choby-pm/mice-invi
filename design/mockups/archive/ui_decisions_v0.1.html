③ UI 의사결정

화면을 실제로 만들기 전에 정해야 할 공통 규칙 12가지입니다. 한 번 정하면 모든 화면에 똑같이 적용되고, Claude Code가 구현할 때도 이 규칙을 따릅니다.

각 항목에서 하나를 눌러 고른 뒤, 맨 아래 선택 결과를 복사해 채팅에 붙여 주세요. 추천안에 모두 동의하시면 "추천안대로"만 적어주셔도 됩니다. 색과 글꼴은 다음 ④ 테마 단계에서 정합니다.

레이아웃
UD-01

콘텐츠 폭

큰 모니터에서 화면을 어디까지 넓힐지. 표는 넓을수록 좋지만, 폼과 문장은 너무 넓으면 읽기 힘듭니다.

추천 이유: 이슈 보드와 대표단 매트릭스는 열이 많아 넓을수록 유리하고, 대리인 입력·상세 화면은 줄 길이를 제한해야 읽기 쉽습니다.

UD-02

PCO 콘솔 메뉴

담당자가 하루 종일 쓰는 메뉴의 형태. 목업에서는 고정 사이드바였습니다.

추천 이유: 메뉴가 12개 이상이라 가로 메뉴에는 다 들어가지 않고, 13인치 노트북에서는 표를 위해 메뉴를 접을 수 있어야 합니다.

UD-03

정보 밀도

한 화면에 몇 줄을 보여줄지. 200명을 다루는 담당자에겐 조밀함이, 가끔 쓰는 사용자에겐 여유가 필요합니다.

추천 이유: 엑셀에 익숙한 담당자는 대량 목록에서 조밀함을 원하지만, 모든 화면이 조밀하면 이슈 상세 같은 판단 화면이 답답해집니다.

UD-04

상세를 여는 방식

목록에서 항목을 눌렀을 때 어디에 상세가 열리는지.

추천 이유: 이슈 상세는 트리와 판단 항목까지 있어 넓은 공간이 필요하고, 서비스 칸 확인은 매트릭스를 보면서 옆에서 여는 게 빠릅니다. 모바일은 모두 전체 화면.

상태와 강조
UD-05

상태 배지 모양

상태 6종(긴급·조치 필요·처리중·완료·대기·무효)을 어떤 모양으로 보여줄지. 색은 테마에서 정하고, 여기선 모양만 정합니다.

추천 이유: "긴급"은 다른 모든 것보다 먼저 눈에 들어와야 합니다. 나머지는 구분만 되면 충분하므로 옅게 두어 긴급을 돋보이게 합니다.

UD-06

긴급 항목 강조

목록에서 긴급 행을 얼마나 세게 강조할지.

추천 이유: 목업의 모바일 카드에서 이미 왼쪽 선을 썼고, 표와 카드 모두에 같은 규칙을 쓸 수 있습니다.

입력
UD-07

필수·선택 표시

대리인 입력은 대부분이 필수입니다(D-UX-05). 필수를 표시할지, 선택을 표시할지.

추천 이유: 영어·한국어가 모국어가 아닌 대리인도 있어 기호 하나에 의존하면 위험합니다. 두 방식을 함께 써서 오해를 없앱니다.

UD-08

라벨 위치

입력칸의 이름을 어디에 둘지. 다국어로 문구 길이가 1.5배까지 달라집니다.

추천 이유: 반응형·다국어 두 조건을 모두 만족하는 유일한 방식입니다.

UD-09

행동 결과 알림과 확인 창

버튼을 누른 뒤 결과를 어떻게 알리고, 언제 "정말 하시겠습니까?"를 물을지.

추천 이유: 확인 창이 드물어야 사람들이 실제로 읽습니다. 메일처럼 한번 나가면 끝나는 행동에만 씁니다.

글자와 구현 기반
UD-10

기본 글자 크기

본문 기본 크기. 운영 도구(PCO·업체)와 초청자 화면(대리인)을 다르게 둘 수 있습니다.

추천 이유: 아이폰은 입력칸 글자가 16px보다 작으면 화면을 자동 확대해 레이아웃이 흔들립니다. 대리인 화면은 16px이 사실상 필수입니다.

UD-11

컴포넌트 기반 (구현용)

버튼·표·입력칸 같은 부품을 무엇으로 만들지. 1인 바이브 코딩이라 AI가 정확하고 일관되게 다룰 수 있는지가 가장 중요합니다.

추천 이유: 부품 코드가 프로젝트 안에 있어 Claude Code가 읽고 고칠 수 있고, ④ 테마에서 정한 값을 토큰 파일 하나로 전체에 반영할 수 있습니다.

UD-12

다크 모드

어두운 화면 지원 여부. 테마 토큰 구조에 영향을 줍니다.

추천 이유: 1인 개발의 검수 부담을 줄이면서, 야간 현장 운영용으로 나중에 켤 수 있는 여지를 남깁니다.
